## 1. Executive verdict

The product is **large and surprisingly complete in breadth** — ~30 UI pages and 174 API routes, almost everything renders, empty-states are thoughtful, dark mode works, and a few pages (Observability, Audit Logs) are genuinely production-grade. Login, RBAC route-guards, execution monitoring, approvals, architecture review, financial dashboards, and a deep Settings surface are all wired.

**But it is not shippable as-is.** The blocking issues are not "does the form submit" — they are trust/correctness and role-usability problems:

1. **Registration half-commits then reports failure** — a real user creation bug (data written, UI says "failed").
2. **The VIEWER role is completely unusable** — any 403 hard-redirects the whole app to a dead-end `/forbidden`, so a VIEWER logs in and can see *nothing*.
3. **A 500 crash** on a QA-dashboard endpoint from an unvalidated date.
4. **A prominent global search bar that does nothing.**
5. Pervasive **"undefined / Unknown / Untitled"** leakage and **contradictory numbers** on the money/dashboard screens that will destroy user trust in a tool whose whole job is oversight of AI spend.

Detail below, severity-ranked.

## 2. Bugs found

### CRITICAL

**BUG-1 — Registration creates the user but reports "failed. Please try again."**
Surface: `/register/:inviteToken` (UI) → `POST /api/v1/auth/register`.
Steps: created a fresh valid VIEWER invite via API, opened the registration page, filled name + password, submitted.
Result: UI showed **"Registration failed. Please try again."** — but the account was in fact **created** (`qa.viewer@example.com` present in `users`, invite flipped to ACCEPTED) and **logs in fine**.
Root cause (backend log): `registration.service.ts:87` — after committing the user + accepting the invite, it calls `JwtService.sign(...)` to auto-login and throws **`secretOrPrivateKey must have a value`**. That particular `JwtService` instance has no secret configured (login's JWT path works, so it's a per-module wiring gap). The user is left created-but-stranded, the invite is burned, and the person cannot tell whether to retry.
Impact: onboarding is broken; retrying returns "Invitation has already been accepted" (400), so the invitee is permanently locked out. Data half-committed.

**BUG-2 — VIEWER role is entirely unusable; any 403 nukes the whole app to `/forbidden`**
Surface: whole app; root cause `src/api/client.ts:138–142`.
Behaviour: the Axios response interceptor does `if (status === 403) window.location.href = '/forbidden'` — a **global** side-effect. A VIEWER logs in, is sent to the default landing page (**PM Dashboard `/`**), which fires manager-tier API calls; the first 403 hijacks the entire SPA to `/forbidden`. Verified: VIEWER is bounced to `/forbidden` from `/` (Dashboard), `/executions`, and `/conversations` — **even though those routes have no role guard**. There is no page a VIEWER can reach.
Secondary effect for higher roles: any shared page containing a single higher-role widget call will 403 → blow the *entire* view away to `/forbidden`, instead of just hiding that widget. This is a fragile, over-broad pattern.
Impact: the VIEWER role (invitable in the UI) is dead on arrival; and the whole app is one stray 403 away from a full-screen forbidden for anyone.

**BUG-3 — 500 on `GET /api/v1/qa-dashboard/anomalies/history`**
Root cause (backend log): `anomaly-detection.service.ts:623` builds `detected_at: { gte: new Date("Invalid Date") }` — the `days`/date query param is neither defaulted nor validated, so calling the endpoint without it produces an Invalid Date → `PrismaClientValidationError` → HTTP 500. This backs the QA dashboard "anomaly history" widget, which will error whenever the param is absent.

### HIGH

**BUG-4 — Global header search is dead**
Surface: the header "Search projects, clients, tickets…" box with the ⌘K affordance (present on every page).
Typing a known value ("Sample"), pressing Enter, and ⌘K all produce **nothing** — no results dropdown, no command palette, no navigation. It is the single most prominent control in the top bar and it does nothing. Either wire it or remove it; right now it actively misleads.

**BUG-5 — Orphaned approval → execution: `GET /api/v1/executions/:id` returns 404 for a queued approval**
The one pending PM approval references execution `5797f024-…`; opening its Review modal fires `GET /executions/5797f024-…` → **404**, so the modal shows "Code diffs not available" and empty QA. A live approval item points at an execution the API can't return — a referential-integrity gap in the seeded/real data path.

**BUG-6 — Financial screens leak `undefined` / `Failed to load` while simultaneously showing data**
- Dashboard **Financial Metrics** widget shows a red **"Failed to load cost data"** banner *and* renders a full ROI $0 table right below it — contradictory.
- `/financial-metrics`: **"Epic undefined"** appears in the Epic Comparison chart and as **"#1 Epic undefined"** in Top-5 Expensive Epics. "Failed to load cost data" on Cost Per Feature.
- Root: several `/financial-metrics/*` and `/costs/breakdown` calls require query params the UI doesn't always send (they 400), and undefined names aren't guarded before render.
Impact: on a spend-oversight product, "undefined" and contradictory error+data is a credibility killer.

### MEDIUM

**BUG-7 — Expired invitations still display status "Pending"**
`/admin/invitations`: two invites with **Expires At 03/07/2026** (11 days past) still show **Pending**, though the status filter offers "Expired." The backend is correct — `GET /auth/invitations/verify/:token` returns **410 "Invitation has expired"** — so this is a **display-only** bug: the list doesn't compute expiry into the status column.

**BUG-8 — `/settings/general` returns 404**
Navigating to `/settings/general` renders the app's 404 page. There is no "General" settings tab (real tabs: cleanup, self-healing, dependency, auto-merge, cost, audit, health, integrations, connected-apps). Dead route — likely a stale link/redirect target.

**BUG-9 — "Est. Exhaustion: today" with zero burn rate**
Dashboard budget forecast shows **"Est. Exhaustion: Jul 13, 2026" (today)** while **Burn Rate $0.00/day** and **Days Remaining: 0**. With no spend the exhaustion math should be "N/A / never", not today. Misleading on an empty project.

**BUG-10 — "UNKNOWN PROJECT" / "Untitled Ticket" fallbacks in the approval queue**
`/approvals` list shows a ticket as **"Untitled" + raw UUID**; the Review modal shows **"UNKNOWN PROJECT"** and **"Untitled Ticket."** Missing-data fallbacks are unfriendly and look broken.

**BUG-11 — Approvals stat contradicts the row**
`/approvals` stat card reads **"OLDEST 0h / Longest wait time"** while the only queued row says **"17 days ago."** The aggregate stat is wrong.

### LOW

**BUG-12 — Constraint form: empty submit gives no feedback**
`/architecture-review/constraints` → Add Constraint → click **Create Constraint** with empty fields: no validation message, the form just stays open silently. User gets no guidance.

**BUG-13 — Invite create: invalid email gives no in-app error**
Create Invite with `not-an-email` and Send: dialog stays open, no in-app validation text (native HTML5 tooltip only, easily missed).

**BUG-14 — Prometheus shows "UP" though the monitoring stack isn't running**
`/observability` reports **Prometheus UP (1ms)** even though the Prometheus container is commented out / not started. Likely a false-positive health probe (reads the app's own metrics endpoint, not an external Prometheus).

**BUG-15 — `clickup/connect` leaks "Project undefined not found"**
`GET /api/v1/integrations/clickup/connect` (no project id) → 404 **"Project undefined not found"** — string-interpolated `undefined` instead of a proper 400/validation message.

## 4. Environment / config issues

**ENV-1 — Checked-in config doesn't self-consistently boot.**
`docker/docker-compose.yml` maps Postgres to host port **5433** (`POSTGRES_PORT` default), but `.env`'s `DATABASE_URL` points at **5432**. With the committed defaults the app cannot reach its own DB. I had to override `DATABASE_URL` to `:5433` to boot. Also port **5432** on this machine is already held by another project's `expo-pos-test-db`. Pick one port and make compose + `.env` agree, and document it in SETUP.md.

**ENV-2 — Registration JWT secret wiring** (this is the root of BUG-1) — the registration module's `JwtService` isn't given a secret even though the global auth JWT is. Worth an env/module-config audit so every signer resolves `JWT_SECRET`.

## 5. UI / UX suggestions

1. **Stop the global-403 redirect (BUG-2).** Handle 403 *locally* per query — hide/gray the widget, show "You don't have access to this section" inline — instead of `window.location = '/forbidden'`. Give every role a landing page it can actually see.
2. **Give VIEWER a real home.** Route each role to a default page it's allowed to open (e.g. VIEWER → a read-only dashboard), not `/` (PM Dashboard) which it can't load.
3. **Forbidden page:** "Required: **Unknown**" is unhelpful and "Back to Dashboard" loops a VIEWER straight back into another forbidden. Show the actual required role and route "Back" somewhere reachable.
4. **Guard every "name" render** against undefined — "Epic undefined", "UNKNOWN PROJECT", "Untitled Ticket" should be real names or a clean em-dash, never the literal word.
5. **Never show an error banner and data at once** (Dashboard Financial widget) — pick one state.
6. **Settings save discoverability:** the "Save Changes" bar only appears after you edit a field. Fine, but add a hint or a always-visible (disabled-until-dirty) Save so users know changes persist.
7. **Login niceties:** add a password-visibility toggle and a "Forgot password?" link (Remember-me is already there).
8. **Invitations:** surface a **copy-invite-link** action (critical while email is unconfigured), and compute **Expired** into the status column (BUG-7).
9. **Empty-state CTAs that dead-end:** "Start Processing Tasks" (AI Capabilities) and similar CTAs should link somewhere real or be hidden until actionable.
10. **Form validation feedback** on Create Constraint / Create Invite (BUG-12/13) — inline messages, not silent.

## 6. Feature-necessity & design review (the "is this even needed?" pass)

You asked specifically to judge whether features/forms are actually needed and to look at design — not just "does it submit." Observations:

**Design — the good.** Consistent shadcn/ui system, coherent sidebar with collapsible groups, working dark mode, and genuinely thoughtful empty states almost everywhere ("No data yet", "Queue Empty 🎉"). **Observability** and **Audit Logs** are standout pages — real data, real filters, useful. This is a competent design system applied broadly.

**Design — the drag.** The overall impression is undermined by (a) undefined/Unknown/Untitled leakage, (b) contradictory numbers on the money screens, (c) a dead global search in the most prominent slot, and (d) a "**Cost visualization coming soon**" placeholder shipped into `/cost`. Individually minor; together they read as "demo, not product."

**Redundancy / features to question:**

- **`/cost` (Cost Analysis) vs `/financial-metrics`.** Cost Analysis is a mostly-placeholder page ("coming soon", "Data not yet available") whose content is already a section inside Financial Metrics. **Recommend merging** — one financial surface, not two, one of which is unfinished.
- **Four separate "review/approve queue" surfaces:** PM Approvals, Go/No-Go **Decisions**, Architecture **Review Queue**, and **QA Review**. Each may be legitimately distinct in this AI-orchestration domain, but from a user's seat they blur together. Worth an explicit map of "which queue, for which decision, for which role" — and consider consolidating into one queue with typed tabs if the audiences overlap.
- **Global header search** — either build it or delete it. A prominent non-functional search is worse than no search.
- **Escalations page** (`/architecture-review/escalations`) renders but is **not in the sidebar** — orphaned. Decide: surface it or remove the route.
- **VIEWER role** — as shipped it can't see anything (BUG-2). Either make it a real read-only role with its own pages, or drop it from the invite role list so you're not offering a broken role.
- **Two "Dashboard" entries** in the sidebar (Favorites → Dashboard, and Overview → Dashboard) point at the same `/`. Minor redundancy; the Favorites section is currently just a duplicate.
- **Jira / Asana "Coming Soon"** cards appear in two places (Connected Apps + Project settings). Fine as a roadmap signal; just make sure they stay clearly non-interactive.

**Net:** the feature *breadth* is arguably too wide for its current *depth* — several surfaces are stubs. I'd cut/merge the stubs (Cost Analysis, dead search, orphaned escalations) and pour that space into making the core loop (ClickUp ticket → AI execution → approval → PR) rock-solid and fully role-usable.

## 10. Real-data pass — Projects & Sync + AI Execution (live DB, real project "List")

The Section 1–9 sweep ran against a fresh seeded DB (only sample projects). This pass re-pointed the backend at the **team's live database** and tested the real, fully-connected project **List → `github.com/Alpharages/SmartPocket`** (ClickUp list connected). To stay safe, the backend was booted with **all AI providers disabled, `FEATURE_AUTO_APPROVE_AFTER_QA` off, and self-healing off** (verified in the running process env), so nothing could auto-execute or auto-push to the real repo.

### 10.1 Projects & Sync — WORKS
- **"Sync from ClickUp"** on project List ran and pulled **~66 real ClickUp tasks**; re-sync is idempotent ("Skipping re-validation – already validated/final").
- **Dispatch is correctly gated** by the status→skill map — log shows `Dispatch skipped: no skill mapping for <id> status backlog / in progress / ready for review`. An AI execution only fires when a ticket enters a **mapped** status (e.g. "to do" → implement). This is the real trigger mechanism.
- **SYNC-BUG-1 (medium):** all **66/66** synced messages logged **`Processing message for task undefined`** — the task identifier is empty at the sync-consumer stage (the ClickUp id resolves elsewhere, but the message's `task` field isn't populated). Indicates a payload/field-mapping gap in the sync consumer.

### 10.2 AI Execution monitoring — works, but the review gate is empty
- **Details/Logs modal works on real runs:** genuine activity timeline — "AI session started", **Model `claude-sonnet-4-6`**, BMAD **`clickup-qa`** workflow, ToolSearch, `mcp__bmad__bmad` calls and tool results. Real telemetry is captured and rendered well.
- **EXEC-BUG-1:** completed executions show **DURATION `0s`** — duration not persisted/shown.
- **EXEC-2 (gap):** the Executions page **"Completed" tab = 0** even though the DB has **11 COMPLETED / 26 total**. The page only lists *active/awaiting* executions; there is **no historical/completed execution view anywhere** in the UI.
- **EXEC-3 (cosmetic/leak):** logs surface raw agent internal text verbatim, e.g. `agentId: … (internal ID - do not mention to user. Use SendMessage …)`.
- **EXEC-4:** QA Results tab shows **"No QA attempt data available"** — QA results aren't linked/persisted, even for `clickup-qa` runs.

### 10.3 PM Approval on real data — **CRITICAL: nothing to approve**
The Review modal on a real awaiting-approval item shows **"UNKNOWN PROJECT"** (it belongs to *List*), **"Untitled Ticket"**, **Files Changed 0**, Complexity —/100, QA Linting/Tests **N/A**, and **"Code diffs not available for this execution"** — yet still offers **"Approve & Push — Code will be committed and pushed to GitHub."**
A PM is asked to approve a **GitHub push with zero reviewable information**. This is the product's central human-oversight gate, and on real data it is empty. (The "OLDEST 0h" vs "2 minutes ago" stat contradiction, BUG-11, also reproduces here.)

### 10.4 End-to-end core loop — not yet proven
- **DB fact:** **0 of 26 executions** captured any `file_modifications` (`files_changed = []` for every row). Every run was a BMAD **`clickup-qa`** (QA/validation) workflow — **none produced code**.
- Therefore the core value loop — **AI implements a ticket → produces a diff → opens a PR** — has **never been successfully exercised** on this project. Only QA-type workflows have run; no implement-execution with a real diff exists to validate, which is also *why* the approval queue has nothing to show.
- **Not done (needs your go-ahead):** triggering a fresh **implement** execution to prove the code-gen loop. It is outward-facing — it clones `Alpharages/SmartPocket`, spends AI credits, and creates a branch. With auto-approve OFF it **halts at the approval gate (no push)**; I'd inspect the resulting real diff/QA and report. Say the word (and which ticket) and I'll run it.

### 10.5 Net on the real project
Projects & Sync is genuinely working against live ClickUp. Execution **monitoring** is real and well-built. But the **thing the product exists to do — supervise AI-written code before it hits GitHub — is unproven here**: no execution has produced a diff, and the approval gate shows "UNKNOWN PROJECT / no diff / Approve & Push". Fixing the empty-review + duration + undefined-task issues and then landing **one real implement→diff→approve→PR** on List is the highest-value next milestone.
